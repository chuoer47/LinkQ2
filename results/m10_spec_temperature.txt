# M10 缺环④ — 概率比接受（T>0 无损）的吞吐代价：实测底稿
# 日期 2026-09-19，机器 4090_public GPU1 + GPU3（两块当时都空闲，每个 run 仍只占一张卡）
# 脚本 benchmarks/06-spec-draft/bench_spec_temperature.py

背景：M10 把接受律从"argmax 相等"换成 Leviathan 概率比 `min(1, q(x)/p(x))`，
T>0 才谈得上分布无损。正确性有 tests/test_spec_acceptance.py（N=20000 实测分布、
TV<0.06），但**加速比从没测过**——概率比路径每步可能多一份 `[bs·(γ+1), V]`
float32 提案分布、一次全词汇 softmax、拒绝后还要从 `norm(max(0,q−p))` 重抽。
这份底稿把这笔税量化。

口径：只计 decode/verify 步（`step()` 返回负数的那几帧），prefill 不进窗口；
每格单跑一次，off 基线与 on 同温度同家族同显存预算。

## 读数

1. **lookup 提案的温度税是真的，但不在算力上**。one-hot 提案让比值测试退化成
   `min(1, q(x)/1) = q(x)`——按目标分布的概率接受，而不是"命中 argmax 才接受"。
   温度升高 → q 变平 → 单个提案词的命中率下降：lookahead natural 的 acc 从
   0.62 掉到 **0.00**（tok/step 1.00，即纯 verify 开销），n-gram natural
   0.68→0.33。
2. **那份 float32 提案矩阵不是成本主体**：lookup 一侧整轮 peak 5.66→5.67 GB，
   说明 one-hot 快路径确实没分配 `[bs·(γ+1), V]`（1.7B γ=4 只需 3.0 MB，本来
   也不该拿它当理由）。softmax/重抽的开销体现在 tok/s 差额里，被接受率变化淹没，
   无法从这组数据单独剥离——要剥离得做同接受率的合成对照，本底稿没做。
3. **draft 提案在"接受律这一项"上税最小**（copy x1.10→x1.05，−4%）：它的提案
   本来就是在目标序列的温度下抽的，比值测试该收就收。natural 掉到 x0.70 属于
   提案质量（acc 0.59→0.34，draft 在 T=0.7 抽偏了），不是接受律的账单。
   **但别把它读成"T>0 就该换 draft"**：自然文本 @T=0.7 三个提案器全亏
   （n-gram x0.95、lookahead x0.89、draft x0.70），没有哪个值得用。真正可用的
   结论是工作负载形状——**T>0 只在复读/模板类文本上开投机**，那里 n-gram
   仍有 x2.68，而且它每步比 draft 便宜得多（γ=4 时 draft 的提案要 18ms 前向，
   见 results/m9_spec_draft.txt），所以 copy 场景也不该换成 draft。
4. **random 家族的两格"加速"是假象**（x1.27→x3.27 / x1.16→x3.77，acc 1.00）。
   探针显示：同一 prompt 在 T=0.7 下模型塌成单 token 循环（64 个里 56 个是
   id 195，末尾 32 个严格周期 1），lookup 白捡全中；greedy 走的是逐年递增的
   "1999-2000 / 2001-2002 …"（13 个不同 token、无严格周期），last-occurrence
   索引每轮猜错下一年的数字，acc 只有 0.29。**这两格量的是轨迹形状，不是投机
   质量。** random 家族只配当"纯 verify 开销"的下界，禁止用来报加速比。
5. **交叉校验**：本脚本的 greedy 行与 M9 的 bench_spec_ngram 一致——1.7B
   γ=4 copy 449.0 vs M9 455.9（−1.5%）、natural 211.5 vs 212.3（−0.4%），
   说明新脚本没有改变被测路径。
