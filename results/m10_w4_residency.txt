# M10 缺环⑥ — Marlin 路径的双份 int4 常驻：实测底稿
# 日期 2026-09-19，机器 4090_public GPU1（当时空闲），conda env qslab
# 脚本 benchmarks/02-w4-quant/bench_w4_residency.py

背景：`w4.auto` 的名字让人以为"按 M 切换后端"只在需要时用一份权重。实际
`CROSSOVER_M=0`（M9 起 Marlin 为主线），v1 pack 全程闲置。这份底稿把"闲置
了多少字节、折成 KV pool 是多少"从口算改成实测。

## 读数

1. **双份常驻与 backend 名字无关**：`w4.auto` 与 `w4.marlin` 两行逐列相同
   （1.7B 均 1.355 GB，8B 6.674 GB）。多出来的一份不是 hybrid dispatch 的代
   价，而是 `W4MarlinBackend` 在 `W4Linear` 的 `qfp/scale` buffer 之外另存一
   份 Marlin 排布的 `_B/_s`（其 `memory_bytes()` 把两者直接相加）。想省掉只
   有走 `w4.v1`（0.26× fp16），代价是 decode 慢一半以上（M9 结论）。
2. **死重量**：1.7B 0.677 GB，8B **3.335 GB**。此前口头估的"8B ≈ 1.9 GB"低
   了近一倍，那次估算是拿单层字节数乘层数得到的，没实际遍历 252 个模块；
   以本底稿为准。
3. **折成上下文长度**（8B @util=0.6）：现有池 1.52 GB ÷ `block_bytes=9216KiB`
   ≈ 161 block × 128 token/block ≈ **2.1 万** token 总容量；腾出 3.335 GB 后
   4.85 GB ≈ 514 block ≈ **6.6 万** token。1.7B 上是 4.41→5.08 GB（+15%）。
   也就是说这笔空间在 1.7B 上是锦上添花，在 8B 上直接决定"能不能开长上下
   文"。
4. `vs fp16` 列以被替换的 Linear 集合为分母（embed/lm_head 不参与 swap），
   是权重口径不是整模型口径。各行 `v1 pack` 相同、`repack` 略高（Marlin 的
   scale 排布多占），符合预期。
5. **口径说明**：`dead v1` 列是实测字节；"if freed" 的 KV pool 是对这些字节
   的算术换算，对应的是一次**当时尚未实现**的改动（Marlin 完成 repack 后释放
   `qfp/scale`）。本底稿只证明这笔空间存在且可观，不证明改后无副作用。改动已于
   同日落地，复测见最后一节——那里同时纠正了这条换算本身的一个错误。

## 2026-09-19 复测：释放落地之后（同一脚本、同一 GPU1、同一 util）

改动：`W4MarlinBackend` 在 repack 之后把 `qfp/scale` 置 None 并声明
`uses_v1_pack = False`；`W4Linear` 据此**不再把 v1 pack 注册成 buffer**，
`memory_bytes()` 改为只算各自实际常驻的那一份。`w4.auto` 在
`CROSSOVER_M = 0` 下 `uses_v1_pack` 为假，于是主线也走同一条释放路径。
`W4Linear.to()` 原先从"第一个 buffer 的设备"推导目标设备，而一个没有
AWQ scale 的纯 Marlin 层现在一个 buffer 都没有，故改为优先取已搬运的
buffer、否则从 `to()` 的入参里取设备（`tests/test_unit_cpu.py` 里
`test_buffer_free_layer_survives_to` 盯这条）。

## 复测读数

1. **死重量归零**：`v1 pack` 与 `dead v1` 两列在 `w4.auto`/`w4.marlin` 上均为
   0.000，`resident` 1.7B 1.355→0.678 GB、8B 6.674→3.339 GB，`vs fp16` 从
   0.52× 降到 **0.26×**。这推翻了原读数 1 的结论"想省掉只有走 `w4.v1`，代价
   是 decode 慢一半以上"：现在 Marlin 主线与 `w4.v1` 同宽（0.678 GB 逐列相同），
   不需要用速度换空间。
2. **原来的 "+220% → 4.85 GB" 换算是错的**，错在把腾出的字节直接加到 KV pool
   上。实测是加到**分配预算**上：8B budget 2.94→6.14 GiB（+3.20 GiB ≈ 3.335 GB，
   对得上），而 pool 两次都只拿到 budget 的 ~51%（1.52/2.94 与 3.16/6.14 同比例），
   所以 pool 实际 1.52→**3.16 GB（+108%）**。按原第 3 条同一 block 口径外推，
   token 总容量 ≈2.1 万→**≈4.4 万**。为什么 pool 只兑现预算的一半没有查证——
   `[kvalloc]` 里 peak/current 与 block 取整都会吃掉另一半，此处**未证**，只记
   录实测比例。1.7B 上 4.41→4.73 GB（+7%），与"+15%"的旧估算同为高估。
3. **`w4.v1` 行仍持有 pack（0.677 GB）**：释放是按 `uses_v1_pack` 条件发生的，
   不是无脑删 buffer。
4. **数值路径未动**：`_B/_s` 与改动前逐字节相同（同一段 repack 代码，只是事后
   释放引用），故 PPL 未复测；全量测试 84/84 通过（3 条新增的 CPU 常驻契约测试
   + 原有 e2e 贪心前缀断言）守住数值面。

## 吞吐点测（同一次改动，1.7B graph decode，GPU1，util=0.5，TOKENS=256）

$ CUDA_VISIBLE_DEVICES=1 MODEL=models/Qwen3-1.7B W4=models/Qwen3-1.7B-qslab-w4-awq2 \
  UTIL=0.5 TOKENS=256 GAMMA=4 python -u benchmarks/05-spec-ngram/bench_spec_ngram.py

copy     offM     179.4      1.00    255      <- w4.marlin
copy     on       388.6      2.45    104   x2.17 (vs marlin base)
natural  off      178.8      1.00    255
natural  offM     179.0      1.00    255
natural  on       364.0      2.28    112   x2.03
random   off      171.4      1.00    255
random   offM     170.3      1.00    255
random   on       207.0      1.35    189   x1.22

1. **释放不减速度**：`w4.auto` 与 `w4.marlin` 三个提示家族逐行相等
   （178.8/179.4、178.8/179.0、171.4/170.3，差 ≤0.6% 且方向不一致）——这正是
   `CROSSOVER_M=0` 下该有的样子，说明省下的 0.677 GB 没有以 decode 速度付款。
2. **绝对值不可跨会话比**：这里 178.8 tok/s 与 M9 记录的 1.7B Marlin 155.2 不同，
   口径差异（util、池大小、机器上其他人的负载）未逐项对齐，**未证**；本次只用于
   同一次运行内 auto vs marlin 的对照。
3. `spec on` 三行顺带确认投机路径在改动后仍工作（x2.17 / x2.03 / x1.22，与
   `benchmarks/05-spec-ngram/README.md` 记录的形状一致）。
