# M11 — 128K YaRN 分档 NIAH：实测底稿
# 日期 2026-09-19，机器 4090_public GPU3（0/2 号是别人的作业，本轮只用当时空闲的 3 号，每个 run 仍只占一张卡）
# 脚本 benchmarks/08-long-context/bench_niah_yarn.py
# 模型 models/Qwen3-8B + W4A16(models/Qwen3-8B-qslab-w4-awq) + KV4(results/smooth_kv4_qwen3-8b.pt)

背景：TODO 第 7 条"128K YaRN demo 未跑"从 M4 挂到现在。真去跑之前发现前提不成立——
runtime **没有 YaRN**：`rope_scaling` 被 Qwen3Attention 接收后直接丢弃，静默无效。
所以本轮先实现 YaRN（`rotary.py`/`config.py`/`qwen3.py` 三处，12 条测试锁在
`tests/test_rotary_yarn.py`，与 transformers 4.57.6 的 `inv_freq`/cos/sin **逐位相同**），
再按 32K / 64K / 128K 分档跑 needle-in-a-haystack。

口径：
* `TIERS="32768:native 32768:yarn:3.2 65536:yarn 131072:yarn"`。32K 同长度并排跑 native 与
  yarn3.2 两列：32K 完全在 native 天花板内，YaRN 那列在此多做了一次 rope 变换，
  所以**两列之差不该读成 rope 的效果**，它是噪声标定。
* 64K/128K 的 factor 由脚本算出 `ceil(ctx/native*100)/100`：65536/40960=**1.6**、
  131072/40960=**3.2**，两者乘回 40960 恰为整数（65536 / 131072），所以这两档的
  rope 天花板就是它们自己的目标长度，不留外推余量。
* 每档 4 个深度 × 2 次 = 8 次，`SEED=0` 固定同一批 needle，`GEN=32`，`UTIL=0.8`。
* 刻意不测的两件事（写明免得后人以为漏了）：
  ① **未缩放 rope 在 64K/128K 的负对照**——native 天花板 40960，越过去是"越界外推"
     而不是一个可比的基线数字，跑出来只会被误读成"YaRN 提升 X%"；
  ② **长上下文 PPL**——需要逐位置 logits，131072 长度的 `[N, vocab=151936]` 是 40 GB
     量级，24 GB 卡上的这套 runtime 结构上给不出（不像 PPL 主线那样有 fp16 参考可绕）。

## 0. 复现命令

```bash
CUDA_VISIBLE_DEVICES=3 \
  MODEL=models/Qwen3-8B W4=models/Qwen3-8B-qslab-w4-awq CALIB=results/smooth_kv4_qwen3-8b.pt \
  TIERS="32768:native 32768:yarn:3.2 65536:yarn 131072:yarn" \
  DEPTHS="0.25,0.5,0.75,0.9" TRIALS=2 GEN=32 UTIL=0.8 \
  python benchmarks/08-long-context/bench_niah_yarn.py
```

```
[probe ctx=131072 d=0.9 len=127484 59.2s ntok=22] 'The special magic number for **magic-7891** is **7891**.<|im_end|>'
```

**每一次生成都自己吐 `<|im_end|>` 收尾，ntok 22–25，远没用到 96（也没用到 32）**
⇒ "截尾"不是预算截的。`Scheduler` 在 EOS 处结束序列（`runtime/scheduler.py` 的 finished 判定），
所以 `GEN` 在这族 prompt 上从不 binding。

## 4. 第一轮为什么作废（仪器缺陷，两条都是本轮学来的口径）

1. **同列 trials 共用同一段 filler ⇒ 前缀缓存命中 ⇒ prefill 不是冷数**。第一轮每列的
   prefill 从 6.7s 一路衰减到 1.0s（32K 列）/ 17.8→2.8s（64K 列），列均值 3.9s、10.6s、33.2s
   全是假数。修法：把每次 trial 的 haystack 在重复段内**按相位错开**（`build_prompt(..., phase=)`），
   于是第二轮每列 prefill 是同一个常数（6.7 / 17.8 / 53.2s），`len=` 也随之逐 trial 抖动。
   顺带确认了 07 号前缀缓存底稿的方向：命中能把 32K prefill 打到 1s 量级，是缓存真的在工作。
2. **答案只印 24 字符 ⇒ 漏检无法归因**。这族 prompt 的开头 24 字符恒为
   `The special magic number`，所以第一轮所有 miss 都长成 `ans='The special magic number'`，
   看不出模型是"没找到"还是"找到了抄错"。修法：片段加宽到 60 字符 + 单独抽 `got=<第一段 6 位数字>`
   与 `exp=` 并排。**第二轮的结论全部依赖这条改动**——没有它，下面读数 3 根本看不到。

另有一条非缺陷的观察：第二轮因为 haystack 相位变了，**同一配置同一批 needle 的结果会动**：
64K 列 8/8 → 7/8，128K 列的逐深度归属整体移动（d0.25 0/2→1/2、d0.90 1/2→0/2）而总量
仍是 3/8。⇒ **每列 8 次样本不足以排序或归因**，这条直接决定了读数 2 的措辞。

## 5. 读数

**① 速度：这是本轮唯一硬核的产品数字。**

| 档位 | rope | 冷 prefill | decode | peak 显存 | 池对当档余量 |
|---|---|---|---|---|---|
| 32K (32768) | native | 6.7 s | **13.3 tok/s** | 12.97 GiB | 4.8× |
| 32K (32768) | yarn 3.2 | 6.7 s | 13.3 tok/s | 12.89 GiB | 4.7× |
| 64K (65503) | yarn 1.6 | 17.8 s | **7.1 tok/s** | 12.92 GiB | 2.3× |
| 128K (131039) | yarn 3.2 | 53.2 s | **3.7 tok/s** | 13.38 GiB | **1.2×** |

* decode 每次长度翻倍掉约一半（13.3→7.1→3.7，比值 1.87 / 1.92）——与"decode 受 KV 读带宽
  支配、每 token 读 O(L)"一致。
* 冷 prefill 每次翻倍 ×2.7 / ×3.0（平方律会是 ×4）：注意力平方项到 128K 还没完全接管，
  但**没拆项**（未证），只报曲线。
* YaRN 在 32K 上不改变时间（6.7s / 13.3 tok/s 与 native 列逐项相同）：它确实多做了一次
  rope 变换 + 一次 `attention_factor=1.1163` 的 cos/sin 缩放，代价在这张表的分辨率以下。

**② 召回：能说的只有"128K 明显差"，不能说"YaRN 有效/无效"。**
128K 3/8 vs 其余三列合计 21/24，Fisher 精确检验单侧 p≈0.012，所以"这一档更差"不是抽样噪声。
但**这条读数说的是长度效应**：本轮没有可比的 128K 基线（未缩放的 128K 是越界外推，
见开头"刻意不测①"），而 32K 两列（6/8 vs 8/8）差 2 例发生在同一份代码、同一批 needle、
只是多跑了一次 rope 变换的两列之间——按 §4 的相位敏感性，这个差不该记账给 YaRN。
⇒ **YaRN 对召回的贡献：未证**。本轮证的是"接上 YaRN 之后，这套 W4+KV4 runtime 能在
131K 位置上端到端跑起来并给出完整回答"。

**③ 失败模式：128K 的漏是"找到了但抄错"，不是"没找到"。**
把两列所有 miss 的 `got/ex` 并排（第二轮 + 探测）：

| 列 | 期望 | 模型给出的 | 形态 |
|---|---|---|---|
| 128K | 921426 | `**92142**` | 前 5 位对，末位丢 |
| 128K | 744039 | `**74403**` | 前 5 位对，末位丢 |
| 128K | 435003 | `**43503**`（探测） | 6 位里少一个 0 |
| 128K | 334130 | `**3341**` | 前 4 位对 |
| 128K | 636685 | `**6368**` | 前 2 位对 |
| 128K | 351589 (key=magic-8226) | `**8226**` | 抄了键里的数字 |
| 32K native | 334130 | `**3341**` | 前 4 位对 |
| 32K native | 983322 | `**9833322**` | 多印一位 |
| 32K native | 636685 | `**6363685**`（探测） | 多印一位 |
| 64K | 983322 | `983222` | 中间两位换序 |

三点结论：
* **漏的形态在 32K 和 128K 是同一种**（数字转写错/截），只是频率上升——32K 一列里就出
  2 例、64K 出 1 例。这不是"长上下文才有的检索失败"，而是一条本来就脆的通道被加压。
* **前 5 位全对（92142/921426、74403/744039）几乎不可能是猜的**（1e-5 量级），而且键名
  出现在尾部问句里、抄键名不需要检索，但**值的前缀不需要**。⇒ 从 12 万 token 外把 5–6 位
  数字捞回来然后写漏最后一位：**塌点在解码/转写，不在注意力查表**。
* 由此暴露一条打分口径缺陷：`value in answer` 把"定位正确、抄错末位"和"完全没找到"记成
  同一个 miss。**本轮不改脚本**（改了就没有可比的两轮），但记进 TODO：长上下文评分需要
  逐位/编辑距离口径，否则这类底稿每次都要人工重读一遍答案才敢下结论。

**④ 池账本：128K 放得下，但只有 1.2× 余量。**
runtime 给每 token 记 `36 layers × 8 kv_heads × (2·head_dim=256) B = 72 KiB`
（`model_runner.py:123-124`，`slot_bytes = 2 * head_dim`）。int4 载荷本身只要
36 layers × 8 × 128 × 0.5 B × 2(K,V) = **36 KiB**/token，也就是当前计费约为真值的 **2×**；
多出的那一半是 scales/对齐，**本轮没有逐字节拆开验证归属**（未证）。
含义：128K + 32 生成 ≈ 9.0 GiB 池，util 0.8 给到 10.56 GiB，`max_num_seqs=2` 已经贴着上限；
再往上（或要并发）要么抬 util，要么先修池计费口径——按 int4 真值计费的话同一张卡能拿到
约 2× 的槽位，这是**下一步该测的东西**，不是本轮结论。

**⑤ 与 M10 那两条产品限制的关系**：本轮全程 greedy（采样温度 1e-6 口径），不触碰
"温度下投机劣化"那条；投机开关本轮为 off（NIAH 测的是长上下文读写路径，不是解码加速）。

## 6. 本轮口径教训（写进 README，防止下次重踩）

1. 长上下文 bench **必须**让同列 trials 的 haystack 相位不同，否则测到的是前缀缓存而不是 prefill。
2. 打印答案必须宽到能看见数字（≥60 字符）+ 单独抽 `got=`，否则 miss 不可归因。
3. 每列 8 次样本在这个模型上会因 haystack 相位整格移动 ⇒ 单档 recall 只用来描述形态，不用来排序。
4. 不要用随机字的 prompt 评投机（M10 已立）；本轮补一条：也不要用"逐位转写长数字"评长上下文
   检索——它把转写通道的脆性记在检索头上。
