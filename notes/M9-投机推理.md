# notes/M9 — n-gram 投机解码接入 runtime

日期：2026-09-18。方案与业界依据：docs/design-m9.md。

## 一、做了什么

**n-gram 投机解码真实接入 M8 引擎**（W4A16 + KV4 + paged + CUDA Graph 全链），
`LLMEngine(spec_method="ngram", spec_num_drafts=γ)`：

- **L0**：`kv4_paged_decode_kernel` 加 `M: constexpr`——grid `(N_Q, bs*M)`，
  row = seq*M + m，读取上界 = L+m。因果性=槽位下界（draft KV 在更高槽，
  天然被各行 mask 排除，不需要显式 mask）。M=1 逐指令等价于原 decode kernel
- **L3**：`qslab/runtime/ngram.py`——numpy 滑窗取末 n 个 token 最后一次出现的后继，
  纯 CPU（vLLM V1 同款）
- **L4**：调度器 verify 分支（propose + 预留 γ 槽位）→ runner `run_verify`
  （M=γ+1 行一次前向，(bs, M) graph 族）→ scheduler `postprocess_verify`
  （greedy 接受 + 提交 + trim 回规范块表）
- **回收走 TGI append-only 路线**（不做 vLLM V0 的 page-table 回滚）：
  被拒槽位随尾部块还回 free list，池内垃圾无人读
- **padding 中立**：无提案的序列 pad 到 γ——接受循环钳制在真实提案数 k 内，
  dummy 永不被接受，该步严格等价普通 decode（温度>1e-3 的序列因此不受影响）
- 混合批（spec/非 spec、greedy/温度）全部安全；跨块、max_model_len 截断、
  eos mid-draft、提案中途预算截断均有路径

## 二、结果（graph，greedy，γ=4；复读=copy-prompt）

| 模型 | 文本 | 基线 | 投机 | 加速 | 接受 |
|---|---|---|---|---|---|
| 1.7B fp16KV | 复读 | 145.5 | 455.9 tok/s | **3.13×** | 3.54 tok/步 |
| 1.7B | 自然 | 145.5 | 212.3 | 1.46× | 1.62 |
| 1.7B | 随机 | 140.6 | 180.8 | 1.29× | 1.44 |
| 8B W4A16KV4 | 复读 | 97.2 | **310.4 tok/s** | **3.19×** | 3.54 |
| 8B | 自然 | 98.0 | 93.2 | 0.95× | 1.05 |
| 8B | 随机 | 95.0 | 89.5 | 0.94× | 1.05 |

- γ=8 复读：1.7B **5.77×**（843 tok/s，6.82 tok/步）
- 诚实口径：8B 自然/随机文本有 ~5% verify 开销（vLLM ngram 同样报告此类开销）
- 复读文本上 spec 输出与非投机 **128/128 token 完全一致**（greedy 数学等价兑现）

## 三、Marlin crossover 修正（M5 结论被 e2e 推翻）

排查 8B 投机首测 0.28× 时发现：`w4.auto` 的 M5 微基准 crossover（v1 赢 M<8）
**在 e2e 上不成立**：

| 测量 | v1 | Marlin | 结论 |
|---|---|---|---|
| M=1 decode 1.7B | 145.0 | 155.2 tok/s | Marlin 赢 1.07× |
| M=1 decode 8B | 54.1 | **91.1 tok/s** | Marlin 赢 1.69× |
| M=5 verify 8B | 65 ms/步 | 11.5 ms/步 | v1 逐行重读权重，Marlin 只读一遍 |

- **M8 遗留"8B decode 55.8 tok/s 未查因"的答案就是 v1 GEMV**；切 Marlin 后
  主线 8B W4A16KV4 decode = **97.2 tok/s（1.75×）**
- 数值无损：Marlin vs v1 logits 相互偏差 **0.047**（两者对 fp16 都是 ~4.0，
  即 W4 量化本身）；PPL 不变，口径不动
- `CROSSOVER_M=8→0`，且 Marlin 可用时**不再构建 v1 权重副本**（原先 auto
  两份 packed 布局同时驻留显存，v1 是死重）
- 微基准教训（与 M8 的 cuBLAS tiling 教训同族）：**单算子固定开销模型
  不能外推到图内 252 层前向**——验收要看 e2e
- 代价：`test_w4_runtime` 的 16-token 逐 token ORACLE 在第 12 位翻转
  （W4 logits 本来就离 fp16 ~4.0，近并列必翻）→ 断言改稳定前 12 token 前缀，
  与 M8 已确立的混沌口径一致

## 四、测试

新增 21 个：kernel 7（对拍/因果性/-1 防护）+ proposer 7 + 引擎 7
（padding 中立、replay-stub 接受率、步数减少、确定性、跨块、短 prompt、graph）

## 五、draft-model proposer（同日完成）

`qslab/runtime/draft.py`：**chained draft model（Qwen3-0.6B）迁入同一 verify 机制**，
`LLMEngine(spec_method="draft", draft_model=...)`。架构 = vLLM V1 的 draft worker
形态：**draft 是第二个完整 runtime**（自己的 ModelRunner：paged int4 池 + 动态
scale 路径的 K 校准 `smooth_kv4_qwen3-0.6b.pt` + decode graph；自己的 Scheduler）。

- **proposer 接口统一**：`propose_batch(seqs)`，n-gram 与 draft 可互换；提案阶段
  从 scheduler 上移到 engine step()（GPU proposer 不该活在调度器里）
- **锁步协议**：每步把 draft 序列截断到 target 已提交前缀（draft KV 低于前缀
  天然有效——因果 + 相同 token；bonus 槽由 catchup query 重写；被拒槽随 trim
  归还）→ prefill（fresh）/γ 步紧循环（免调度往返）→ 提案 = 超出前缀的 token
- 修 3 个 bug：scheduler/model_runner 的 spec_method 只认 "ngram"（draft 永不进
  verify 分支）；`_sync` 不重置 `num_cached_tokens` → 漂移后 hash_blocks 越界
  （长跑必崩）；`may_append` 非幂等（trim 后的表已含所需块，会重复分配）
- **结果（γ=4，graph，greedy）**：

| 配置 | 复读 | 自然 | 接受 |
|---|---|---|---|
| 1.7B + 0.6B draft | 165.4 tok/s（1.12×） | 93.1（0.63×） | 4.24 / 2.36 tok/步 |
| 8B W4A16KV4 + 0.6B | 143.5（**1.47×**） | 71.6（0.73×） | 4.24 / 2.08 |
| （对照）8B + n-gram | 310.4（3.19×） | 93.2（0.95×） | 3.54 / 1.05 |

- **诚实结论**：draft 的优势在"提案质量"（自然文本 2.08-2.36 tok/步，n-gram
  只有 ~1.05；复读两者都近满），但 0.6B 每步 4.53ms × γ=4 = 18ms 提案开销，
  自然文本下入不敷出。
- **瓶颈精确归因（CUDA event 实测，修正初版"一半是 Python"的错误估计）**：
  draft 步 **100% GPU-bound**（CPU prepare+submit 仅 0.25ms 且完全重叠，
  tolist 的 4.27ms 只是等 GPU）：
  | 成分 | 耗时 | 说明 |
  |---|---|---|
  | 28 层 × 7 权重 GEMV（840MB） | 2.50ms | **352GB/s，仅 4090 峰值 35%**——M=1 小 GEMV 延迟限制带宽（单个 gate_proj 实测也只 471GB/s） |
  | 图内其余 kernel（attn/norm/RoPE/KV store 等 ~280 个小 kernel） | 1.70ms | bs=1 时每个 kernel 太小，启动间隙+低占用 |
  | lm_head（311MB 大 GEMV） | 0.32ms | **963GB/s 接近峰值**——证明不是硬件而是小 kernel 形状问题 |
  | argmax + 同步 | 0.01ms | 可忽略 |
  杠杆排序：**W4 化 draft body**（840→210MB，即按同带宽也 ~0.6ms）；融合小 kernel
  （省 1.7ms 的大头）；lm_head 无需动。γ=4 已是该开销结构的最优点
- 测试：`tests/test_draft_spec.py` 4 个（复读/自然接受率、确定性、清理与
  规范块表、多序列）；新增校准 `results/smooth_kv4_qwen3-0.6b.pt`

## 六、W4 draft 实验 + γ 帕累托扫描（同日，结论修正）

**W4 化 draft（0.6B 过自家 quantize 链路，awq，196 层）——收益为零，预测修正**：
- GEMV 段确实 2.50→1.19ms（权重 840→210MB）✓ 量化本身有效
- 但步时不变（4.53→4.72ms）：profiler 实测**每步 2241 个 kernel**，
  w4a16_gemm 196×1.19ms + attention 28×0.49ms + lm_head 0.32ms 之外，
  **~1500 个未融合的 elementwise/copy 占 ~2.6ms**（norm/rsqrt/rope/residual/
  silu·mul + W4Linear 每层的 act_scale 除法与 copy）——bs=1 时 kernel 数是税，
  不是字节数。我此前"带宽受限、W4 化后自然文本 1.1×"的预测错了（假设错）
- **修正后的正解：kernel 融合**（2241 → ~300 才能到 ~2ms/步；torch.compile
  或手写融合层，后续工程项）

**γ 帕累托（8B + 0.6B draft，γ∈{1,2,3,4,6,8}）**：
- copy 单峰：**γ=6 达 156.0 tok/s（1.59×，5.97 tok/步）**，γ=8 回落
  （接受饱和 ~6.8，提案成本线性涨）
- natural 单调劣化：**连 γ=1 都是 0.94×**（接受 0.43/步 × 省 10.2ms =
  4.4ms ≈ 恰好抵一个 draft 步 4.5ms）——接受率买不回成本
- 与 n-gram 对照（γ=4：copy 3.19×、natural 0.95×）：**当前形态下 draft
  模式无任何场景胜出**（提案免费 vs 4.5ms 的差距）；draft 的存在意义
  （自然文本接受 2.08-2.48 vs n-gram 1.05）要兑现，前提是 draft 步
  降到 <2ms（即 kernel 融合）

## 七、draft kernel 融合落地（同日，torch.compile）

按 §六结论上融合：**draft 的 0.6B 用 `torch.compile(dynamic=True)` 编译**，
attention 用 `torch._dynamo.disable`（全局 Context 会搅 dynamo 守卫；disable 后
在 attention 处 graph-break，**层间全部 elementwise 交给 inductor 融合**——正是
§六定位的 ~1500 个小 kernel）。编译产物照常被录进我们手写的 CUDA Graph。

- **draft 步 4.53 → 2.59ms（1.75×）**，FP16（W4 已证伪，无需量化）
- 踩坑：**dynamo 守卫把 inference_mode 状态编码**——init 的捕获预热在
  inference_mode 下编译，propose 循环不在 → 首个真实提案触发 ~5s 重编译
  （γ=1 扫描点被它污染成 0.30×，一度误判为异常路径）。修复：DraftProposer
  `_warm()` 在 init 时做一次 dummy propose 把编译提前
- **γ 帕累托（融合后，冷启动诚实口径）**：
  - 自然文本：**γ=2 = 114.4 tok/s（1.17×）最优**，γ≥3 回到 1.0× 以下
  - 复读：**γ=8 = 225.1 tok/s（2.30×）**（γ=10 回落），单峰右移
  - vs 未融合：自然 γ=2 0.85→1.17×；复读 γ=8 1.45→2.30×
- **分工格局**：n-gram 仍统治复读（3.19×，提案免费）；**draft 现在统治自然
  文本（1.17× vs n-gram 0.95×）——draft model 的存在意义兑现**
- config：`compile`/`compile_mode`（仅 draft 开）；11 spec 测试全绿

## 八、遗留

- 温度采样的概率比接受律（Leviathan full rejection sampling）——当前仅 greedy
- draft 提案阶段的吞吐优化：**正解是 kernel 融合**（W4 已实验证伪——
  2241 kernel/步的固定开销主导，见 §六）；候选：torch.compile(max-autotune)
  或手写融合层（norm+rope+residual、silu·mul、W4Linear 输入除法）
- `qslab/engine/spec/` 旧投机栈未迁移未删除（lookahead/dynamic 模式）

## 九、前缀缓存修复复活（同日）

M8 的静默错答 bug（命中哈希的前缀只在 int4 池、flash-attn 却按全长
`cu_seqlens_k` 消费错位的尾段行）按物化路线修复，`ENABLE_PREFIX_CACHE=True`
默认开启：

- **`materialize_kv`**（paged_decode.py）：池槽位 → fp16 的反量化
  （uint32 无索引 kernel → view(int32) 后 gather；K 静态/V per-token 组 scale）
- **`prepare_prefill` 算一次 slot 计划**（`Context.prefix_slots/prefix_plan`）
  下发给全部 28 层——第一版每层 tolist() 重算，28 次 GPU 同步（~14ms）比
  省下的 prefill 还贵，教训同 draft 融合：**跨层共享的计划绝不能放层内**
- attention prefill 分支：一次反量化整批前缀 + cat 拼接 → flash-attn 拿到
  与声明长度一致的 K/V
- **顺手修了同族 bug**：chunked prefill 第二块同样只拿本块 K/V 却声明全长
  （prompt>16384 才触发，从未暴露）——物化的 `cached = cu_k − cu_q` 天然
  覆盖哈希命中与上一块两种来源，一次修复两个 bug
- spec 路径补 `hash_blocks`（投机提交也会填满块，否则投机序列永不产生
  缓存条目）；哈希边界天然不含 bonus 位置（num_cached+scheduled = num_tokens−1），
  拒绝槽位的垃圾不会被缓存
- 精度口径：命中请求 prefill 从 exact fp16 变 int4 反量化——KV4 已接受噪声
  的延伸；测试断言 hit==hit 精确、hit vs cold 首位 token（老 bug 恰好腐蚀
  那一位），不逐 token 断言（M8 混沌口径）
- **结果（bench_prefix_cache.py，3800-token 前缀 + 11 后缀）**：
  - 1.7B：TTFT **136.2 → 49.9ms（2.73×）**
  - 8B：TTFT **558.3 → 63.0ms（8.86×）**
- 测试：prefix_cache 4 个（命中正确+确定、命中确实发生、共享前缀+新后缀、
  chunked prefill）+ materialize 往返对拍；全量回归绿（32 非 e2e + 27 e2e）
