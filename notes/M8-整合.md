# notes/M8 — nano-vllm runtime 整合

> 目标：把 nano-vllm 的 L3 runtime（paged KV + 连续批 + CUDA Graph 骨架）接进 qslab，
> 保留我们的量化栈（W4 权重 + KV4）与模型定义路线。
> 源码 `.cache/nano-vllm-main`（MIT）；产物 `qslab/runtime/`。

## 交付

| 项 | 状态 |
|---|---|
| runtime vendor（调度/分页/块管理/图捕获骨架） | ✅ |
| int4 分页 KV 池（slot 映射，替代 nano-vllm 的 fp16 池） | ✅ |
| Triton store / decode 内核（K 静态 per-channel + V 动态分组） | ✅ |
| SmoothAttention 离线校准（`scripts/build_smooth_kv.py`） | ✅ |
| **1.7B e2e 与 HF oracle 逐 token 一致** | ✅ |
| CUDA Graph 验证 | ✅ 捕获 4 桶、输出无损、6.5× 加速 |
| 连续批吞吐 | ✅ 8 路 1048 tok/s |
| W4 权重接入 | ✅ 1.7B 逐 token 无损（eager 与 graph） |
| 8B 验收 | ⚠️ prefill 对齐、输出连贯；KV4 精度不足见 §六 |

## 一、为什么 K 的量化方式必须改

### 现象
runtime 接上 int4 池后，prefill 出的第一个 token 正确，decode 第一步就分叉成乱码。

### 归因过程（值得记的弯路）
1. **先抓到一个真 bug**：store 写 offset-binary（`nib = qi + 8`），decode 读
   two's-complement（`nib>=8 ? nib-16`）。同一字节两种解释，所有值整体偏 8 个量化级
   （≈8×scale）。统一为 offset-binary 后，直连测试从 2e-4 收敛到 3e-5。
2. **但 e2e 仍分叉**。此时做了两个对照：
   - fp16 存取同一套引擎机制 → 与 HF 逐 token 一致
     ⇒ slot 映射 / RoPE / 残差 / 采样**全对**，锅在 int4 路径
   - 用 HF 单独量化 K/V 复现 → 复现
3. **量化误差定位**（28 层平均，post-RoPE K）：

   | 方案 | 平均绝对误差 | 相对 \|K\| |
   |---|---|---|
   | per-token per-head（原实现） | 0.654 | **23%** |
   | per-channel（跨 token 分组） | 0.100 | 3.6% |

   Qwen3 的 K 经 `k_norm + RoPE` 后有**固定离群通道**：layer0 实测 amax 313、
   均值 2.8（**111×**）。per-token 量化时步长被离群通道拉大，99% 的通道被压成 0。
4. **第二个真 bug**：`v` 来自 `qkv.split()`，是**非连续视图**（行 stride = 整个 qkv
   宽度 4096，而非 `H*D=1024`）。store kernel 按连续布局读 → 存的 V 全是垃圾。
   flash-attn 自己处理 stride，所以 **prefill 无恙、只有池里的 V 是错的**——
   这也是为什么"第一个 token 对、之后全崩"。

## 二、KV4 的量化方案（有行业依据，非自创）

调研了四家的实际做法：

| 系统 | KV scale 来源 | 粒度 |
|---|---|---|
| vLLM (FP8 KV) | **离线校准存 checkpoint**，官方标 [Recommended] | per-tensor / per-head |
| TensorRT-LLM | NVFP4 KV 明确要求 offline 量化 | 每 16 元素块 |
| KIVI | 动态 + **残差窗口**（最新 R 个 token 保持 fp16，攒够 G 个才量化） | K per-channel / V per-token |
| QServe | **SmoothAttention**：离线 `λ_i = max\|K_i\|^0.5` 压平离群，再量化 | |

**共同点：没有一家在生产里做「回头重量化旧 token」。** 要么离线定死 scale，
要么结构性消除离群，要么用残差窗口绕开。

### 我们的取舍

K 的 per-channel scale 若**动态**求，新 token 到达时必须重算已存 slot 的 scale——
写入地址依赖数据，**CUDA Graph 捕获不成立**。所以：

- **K：int4 + 静态 per-channel scale**（校准一次，写入纯 slot 驱动 → graph 安全）
- **V：int4 + 动态 per-token group=64**（V 的离群是 token 局部的，写入仍与数据无关）

为让静态 per-channel scale 够用，先做 **SmoothAttention** 把离群压平：

```
λ_i = λ_{i+D/2} = max(max|K_i|, max|K_{i+D/2}|)^0.5      (QServe Eq.9)
Q' = Q·Λ,  K' = K/Λ⁻¹                                    (Eq.7)
```

RoPE 把通道 `i` 与 `i+D/2` 配对，λ 必须**成对相等**才能与 RoPE 交换——这是
QServe 明写的硬约束，我们照做。

实测：K 通道间离散度 **31.3× → 6.9×**。

### 落点：λ 放在哪
qslab 的 `q_norm`/`k_norm` 是**按头共享**的单向量 `[D]`，而 λ 是 per-head `[H,D]`，
折不进 norm 权重。改为在 attention 内做两次逐元素乘（每层 ~4M FLOP，可忽略），
graph 合法。

## 三、采样与正确性证据

```
HF oracle : [12095, 13, 576, 6722, 315, 9856, 374, 19846, ...]
runtime   : [12095, 13, 576, 6722, 315, 9856, 374, 19846, ...]   ← 逐 token 一致
```

对照实验（同一脚本、同一引擎）：
- `K fp16 / V fp16` → 匹配   ⇒ 引擎机制正确
- `K int4 per-token（无平滑）` → 分叉
- **`K int4 静态 per-channel（有平滑）/ V int4 group=64`** → **匹配**

> 注意：早期"直连测试 CONSISTENT"的结论是**同侧自洽**——参考解量化用了和内核
> 相同的错规则，所以"互相一致"但双双偏离源数据。**判断量化正确性必须以源数据为
> 基准，不能以内核 vs 内核的参考为基准。** 这个教训已写进 `tests/test_kv4_paged.py`。

## 五、CUDA Graph 与连续批（M8-S3）

| | eager | graph |
|---|---|---|
| decode, batch 1, 128 tok | 22.8 tok/s | **148.7 tok/s**（6.5×） |
| 连续批 8 路 × 64 tok | 286.7 tok/s | **1048.2 tok/s** |

捕获桶 `bs=[1,2,4,8]`（由 `max_num_seqs` 决定），graph 输出与 oracle 逐 token 一致。
**这兑现了静态 K scale 的设计理由**：写入地址只由 slot_mapping 决定，不依赖数据，
所以能被捕获。

### 批处理下单条输出会变——查清了，不是缺陷

单条跑和 8 条一起跑，同一条的输出在若干步后会分叉。逐项排除：

| 检验 | 结果 |
|---|---|
| flash-attn varlen 打包不同长度同伴 | **Δ=0**（bit-exact） |
| 我们的 batched logits vs HF batched logits | **top-1 一致 8/8**，maxΔ 0.055 |
| 输出是否依赖同伴**内容** | **否**（4 个不同同伴逐 token 相同） |
| 内核重放同一状态 3 次 | **Δ=0**（确定性） |
| **HF 自己 solo vs batched** | **同样漂移 0.021~0.033** |

根因：批大小改变了每个密集层 GEMM 的 M 维，cuBLAS 据此选不同 kernel/split-k，
归约顺序随之改变 → logits 末位漂移 → 在近似平局处 argmax 翻转。
**这是 GPU 库的固有属性，HF 同样如此，不是引擎缺陷。**

> 判断标准：批处理结果只需与**参考实现的批处理结果**一致（已验证 8/8），
> 而不是与"单条跑"一致。

## 六、W4 接入与 8B 验收（M8-S4）

### 为什么要拆掉融合投影
打包 checkpoint 按 **HF 模块名**存权重（`q_proj`/`k_proj`/`v_proj`…），AWQ 的
输入缩放也按**逻辑模块**存（各 shard 的 s 互不相同）。融合的 `qkv_proj` 只有一个
输入，装不下三个不同的 s——融合会静默丢掉 AWQ 缩放。实测融合只值 **3%**
（149.1 → 144.8 tok/s），不值得。拆开后 checkpoint 直接按名匹配，且顺带根除了
V 非连续（`qkv.split` 视图）这个隐患。

### 途中修的两个真 bug

1. **`lm_head` 维度声明反了**。`primitives.Linear` 是 `[out, in]`，而 HF 存的是
   `[vocab, hidden]`；1.7B 因为 `tie_word_embeddings` 共享了 embed 权重而**侥幸
   通过**，8B 不 tie 就在加载时崩。新增 `LMHead`（权重 `[vocab, hidden]`）。
   > 教训：只有 tie-embedding 的小模型能掩盖这类维度错误。

2. **`w4a16_gemm` 启动在默认流**。`w4a16_gemm_api.cu` 里
   `w4a16_gemm_kernel<<<grid, 128>>>(...)` **没有 stream 参数** = legacy default
   stream。而 CUDA Graph 捕获发生在旁路流上，**默认流上的 kernel 不会被录进图**，
   回放时整个 GEMV 被跳过 → 输出全 0。改为 `getCurrentCUDAStream()`。
   > 症状极具误导性：graph + fp16 正常，graph + W4 输出全 0——看起来像量化问题，
   > 实为流语义。任何自定义 kernel 都必须显式使用当前流。

### 8B 结果

| 检查 | 结果 |
|---|---|
| prefill logits vs HF（fp16 权重） | **max\|Δ\| = 0.023** |
| prefill logits vs HF（W4 权重） | max\|Δ\| = 0.45，top-1 4/4 正确 |
| decode 吞吐（graph） | **55.8 tok/s** |
| **KV4 的 PPL 代价** | **+0.369（16.06 → 16.43，+2.3%）** |

### KV4 的 PPL 代价（这是该看的指标）

**「逐 token 无损」不是可达指标。** 4-bit KV 下 greedy 解码是混沌的：引擎可以每步
都算得对，但只要某一步的 logit 间距小于量化误差，就会翻转，之后全变。实测两个
模型都只有 **1/8** prompt 与 HF 完全一致，但前 6–14 个 token 相同——这个分布是
混沌，不是缺陷。单条 prompt 的"无损"是运气。**PPL 才是正确的仪器**（docs/03，
M7 亦如此）。

测量方法（`benchmarks/bench_ppl_kv.py`）：**在 HF 上直接模拟方案**，绕开 runtime
——方案是量化的属性、与存储位置无关，这样没有调度器/显存/图捕获的干扰。
拦截点很关键：K/Q 必须在 **post-RoPE** 处量化（挂 `k_proj` 会量化到 norm 之前、
rope 之前的值，测出的是别的东西——我第一次就是这么错的，得到 PPL 2077）。

| 配置（8B，10 docs） | PPL | 相对 fp16 |
|---|---|---|
| fp16 基线 | **16.059** | — |
| 仅 K int4（含 SmoothAttention） | 16.202 | +0.143 |
| 仅 V int4（分组 64） | 16.146 | +0.086 |
| **KV4（K+V）** | **16.428** | **+0.369（+2.3%）** |

1.7B：26.699 → 27.798（**+1.098，+4.1%**）

自校验：8B fp16 基线 16.059 与 M4 矩阵记录的 16.07 吻合。

**归因**：K 与 V 单独各 +0.14 / +0.09，合起来 +0.37——**超加性**，两处误差经注意力
层叠加放大。

### 更正：此前几轮的三个错误结论

1. ~~"8B 静态 K scale 覆盖不足（18~66 通道超限）"~~ — 错。我按 head 归约了
   `[T,H,D]` 却与 `[H,D]` 表比较，广播出假数字。正确的 per-(head,channel) 测量：
   超限比例 0.0–0.2%，可忽略。
2. ~~"逐 token 无损是可达指标"~~ — 错，见上。
3. ~~"8B 的 KV4 精度不足 / 是 W4 的问题"~~ — 来回误判过两次。现在有干净的数字：
   KV4 代价 +0.369，W4 权重本身的 logit 偏差 0.45（主链同值，属已接受的量化损失）。

## 七、前缀缓存：一个静默错答的 bug（已修）

nano-vllm 的 block manager 会按 token 哈希复用块。命中时 `prepare_prefill` 让新
chunk 从 `num_cached_tokens` 开始，并设 `context.block_tables`——**被复用的前缀只
存在于 int4 池里**。而我们的 prefill 走 flash-attn 读刚算出的 fp16 K/V、**从不读池**，
于是 attention 只看到新后缀，序列静默丢掉整段前文。

实测（1.7B，132-token prompt，同一引擎第二次提交）：

```
run1: [576, 3840, 315, 24231, 6009, ...]
run2: [0, 220, 576, 3840, 315, ...]      <- 不同
```

**为什么一直没暴露**：`can_allocate` 只检查**整块**（`seq.num_blocks - 1`），所以
单块以内（<128 token）的 prompt `num_cached_blocks` 恒为 0。此前所有测试用的都是
短 prompt。

**修法**：暂时**禁用前缀复用**（`BlockManager.ENABLE_PREFIX_CACHE = False`）。
重新启用的前提是让 prefill 能从池里物化 int4 缓存前缀——那是把 varlen attention
改成「新 token 用 fp16 + 前缀从池里读」的混合路径，是个独立的工程。禁用比留着一个
会静默出错的优化更安全，代价只是长公共前缀的重复计算。
