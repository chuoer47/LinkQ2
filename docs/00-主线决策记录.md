# 00 - 项目主线决策记录

> 项目代号：**qserve-lab**（自研轻量 LLM 量化推理引擎）
> 记录开始：2026-09-14
> 本目录用途：固化所有主线讨论的结论，作为后续整体设计与推进的唯一依据。

---

## 1. 项目定位

- **目标**：搭建一个属于自己的轻量量化推理系统，作为简历项目（"简历的包装项目"，不追求学术发表）。
- **原则**：不从零造轮子——借鉴成熟框架（vLLM / Marlin / KIVI / QServe / DeepCompressor）的设计，自己组装成一个紧凑自洽的引擎；每个部件都有官方参照物可对比。
- **与 LinkQuant 的关系**：LinkQuant 是"量化算法侧"（怎么量化），本项目是"推理引擎侧"（量化完怎么跑）。方法论一致（手写 → 对比官方 → 写笔记），Qwen3-1.7B/0.6B 等资源可共用。

## 2. 选型演变（重要决策链）

### 2.1 最初调研：W4A16 vs W8A16 推理链路选型（2026-09-14）

调研并核实了候选仓库（GitHub API 实时验证，有搜索结果与实际不符的坑）：

| 仓库 | 状态 | 结论 |
|---|---|---|
| mit-han-lab/llm-awq (3633★) | 活跃 | W4A16 全链路，MLSys'24 Best Paper |
| IST-DASLab/marlin (1146★) | 2024-09 停更 | W4A16 高吞吐 kernel，sm≥8.0，4090 可用 |
| efeslab/Atom (347★) | 2024-07 停更 | 绑死 TRT-LLM v0.7.1，不建议 |
| mit-han-lab/omniserve (858★) | 2025-03 | QServe W4A8KV4，MLSys'25 |
| ModelCloud/GPTQModel (1253★) | 活跃 | AutoGPTQ 继任者 |
| casper-hansen/AutoAWQ | **已归档** | 排除 |

**W8A16 被否**：学术上没故事（weight-only 8bit 几乎无加速），kernel 简单，简历区分度低。W4A16 是甜点位。

### 2.2 曾选 QServe（W4A8KV4）→ 评估后主动降级

用户最初选 QServe 复刻。全面评估（4090 服务器现状 + OmniServe 源码逐文件核实）后确认技术上可行（setup.py SUPPORTED_ARCHS 含 8.9；论文 L40S 与 4090 同为 sm_89），但后续讨论认为：
- QServe 完整复刻太复杂（serving 栈：in-flight batching、paged attention、多套 fused kernel）
- 用户自述对领域了解不多，希望**搭建属于自己的量化系统**而非复刻别人的系统

### 2.3 最终主线：W4A16 + KV4，砍掉 A8（2026-09-14 定版）

- **W4A16 = 成熟部分**：反量化 + FP16 tensor core，参考资料海量，vLLM 是现成对照组
- **KV4 = 自己的东西**：KV cache 4bit 量化是差异化点（QoQ/KIVI 一系），保留
- **砍掉 A8 = 砍掉 QServe 最难 30%**：W4A8 渐进量化 GEMM、compute-aware weight 重排是为 A100 大 batch serving 设计的，对 decode-only 场景意义小
- **砍掉 serving**：in-flight batching、paged attention v1、多卡、70B 全不做。decode-only 单请求（显存带宽受限区间 = W4A16 收益区间）
- 杀手级 demo：**单张 4090 跑长上下文**（KV4 让 KV cache 缩 4×）

## 3. 模型选型定版：Qwen3-8B（2026-09-14 最终拍板）

决策链：Qwen3-8B → 用户提出 Qwen3.8（最新）→ 调研后发现问题 → **回定 Qwen3-8B（求稳）**。

Qwen3.8 调研结论（为何不用）：
- Qwen3.8 系列最小就是 27B（55.6GB BF16），单卡 24G 放不下；27B-FP8 也要 ~28G
- Qwen3.8-27B 是 hybrid 架构（64 层 = 48 linear attention + 16 full attention，model_type `qwen3_5`），KV4 只作用于 1/4 的层，叙事别扭
- vLLM/awq/KIVI/Marlin 等成熟方案全部不支持该架构，"借鉴成熟框架"前提消失
- （备选 Qwen3.5-9B 也是 hybrid：32 层 = 24 linear + 8 full，同样有此问题，但曾作为折中推荐，用户最终求稳选 Qwen3-8B）

Qwen3-8B 关键参数（已核实）：
- 32 Q heads / 8 KV heads（GQA）、36 层、hidden 4096、head_dim 128、SwiGLU (12288)
- QK-Norm、RoPE theta 1e6、tied word embeddings、~8.2B 参数
- 原生 32K 上下文，YaRN 4× 可扩至 128K（rope_scaling factor=4.0）
- Apache 2.0，ModelScope 可下载（网络约束友好）
- 同族 Qwen3-0.6B（服务器已有）可做 draft model

## 4. 技术栈定版

| 部件 | 方案 | 借鉴对象 |
|---|---|---|
| 目标模型 | Qwen3-8B（32K 原生，YaRN 128K） | — |
| 权重量化 | W4A16 group-wise | Marlin / AWQ kernel 的反量化+MMA 数据流（自写简化版 kernel） |
| KV cache 量化 | KV4 不对称量化 | KIVI（per-channel K / per-token V + 前几层保 FP16）+ QServe SmoothAttention |
| 投机推理 | 经典 draft-model 投机采样（Leviathan/Chen 2023，拒绝采样，无损） | vLLM spec-decode；**明确不碰 EAGLE3/Medusa（要训练 draft head，超出预算）** |
| draft model | Qwen3-0.6B（服务器已有，同 tokenizer） | — |
| kernel 语言 | CUDA（吃 LeetCUDA 积累），不用 Triton | — |
| 量化器参照 | DeepCompressor（已 vendor 在 LinkQuant）+ llm-compressor | — |

**投机推理 × KV4 的乘法效应**（项目"组合拳"亮点）：target 一次验证 γ 个 draft token = 一次读 γ 个 KV，KV 带宽瓶颈被摊薄；与 W4A16（权重带宽↓）、KV4（KV 带宽↓）打的是同一 roofline 上不同瓶颈。三者叠加实测数据是论文里很少有的数据点。

## 6. 资源现状（2026-09-14 实测）

- 服务器 4090_public：4× RTX 4090 D（24G, sm_89），当前 GPU3 最空（2.4G 占用）；磁盘可用 226G（总盘 87%）；253G 内存
- `leetcuda` env：nvcc 12.4 + gcc-13 (conda-forge) + torch 2.5.1+cu124，编译 CUDA kernel 的完整方案已验证
- `vllm` env：torch 2.8.0+cu128，现成对比基线
- `linkquant` env + vendor 里的 deepcompressor：量化器参照
- 模型已有：Qwen3-0.6B (1.5G)、Qwen3-1.7B (3.8G)；需新下 Qwen3-8B (~16G)
- GitHub 走 ghfast.top 代理；HF 走 hf-mirror.com；模型走 ModelScope
- 环境铁律：所有 pip/conda 操作只在新项目 env 内进行，不污染其他 env

## 7. 已知风险（诚实清单）

1. KV4 精度是真正的坎：裸 KV4 会打爆 PPL，必须 KIVI 式技巧（per-channel K + 前几层 FP16）或 SmoothAttention 式保护
2. kernel 性能对标要合理：W4A16 GEMM 在 decode 区间做到 FP16 的 1.5~2× 即成功（带宽受限），不追 Marlin 极限
3. 共享服务器 benchmark 噪声：挑空闲时段 + 锁 GPU + 多轮取方差，笔记如实交代
4. 投机推理 draft 占显存 ~1.5G，M4 显存预算：8B W4 ~5G + 0.6B ~1.5G + KV4@32K ~1G，24G 富余
5. 新模型 Qwen3-8B (~16G) 需下载
