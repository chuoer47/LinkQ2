# 怎样验证 Kernel 的设计

低位表示改变了数据，分块与并行归约又改变了执行过程。验证需要把这两种影响拆开，才能判断一个差异来自量化方案、计算精度，还是实现错误。

本篇围绕前两篇中的设计选择说明验证方法。具体测试入口见 [tests/kernels](../../tests/kernels)，性能与模型质量入口见 [Benchmark](../../benchmarks/README.md)。

## 1. 先区分量化误差与执行误差

可以把结果理解为三个层次：

$$
\text{原始浮点数据的计算}
\quad\longrightarrow\quad
\text{恢复量化值后的参考计算}
\quad\longrightarrow\quad
\text{实际融合内核的计算}.
$$

第一段差异来自数据表示改变，第二段差异来自实际执行方式。若只比较最左和最右，就无法知道一个较大的误差究竟应该改算法，还是检查打包、寻址和归约。

### W4A16 的参考

先从同一份逻辑整数、scale 和 zero point 恢复浮点权重，再与融合算子对照。这样，两侧使用的是同一组量化值，测试能够集中检查打包方向、组索引、零点解释和矩阵计算。

有输入缩放时，还需要保持比较的数学对象一致。AWQ 的在线路径在乘法前缩放输入，fake 模型则可以把缩放折叠进浮点权重；两者的浮点舍入位置不同，不能仅凭结果不逐 bit 相同就认定实现错误。

实际量化方案相对原模型损失多少质量，由[完整权重包 PPL](../../benchmarks/compression/weights/README.md)另外衡量。

### KV4 Attention 的参考

先按页表找到实际 slot，独立解包缓存整数，乘上缓存中真实保存的尺度，再用浮点 Attention 计算参考输出。参考侧也要使用相同 GQA head 映射、有效长度和因果范围。

这能检查“给定这份缓存，Attention 是否正确地使用它”。另用小张量检查写入后的整数码、尺度和恢复误差，验证缓存生产过程。最后才用[整模 KV4 PPL](../../benchmarks/runtime/kv4/README.md)观察误差在模型中传播后的影响。

测试中可以完整恢复一个小缓存，换取清楚、独立的参考；正式 decode 使用流式读取，避免为每个 token 付出这种完整恢复成本。

## 2. 地址与因果关系，怎样单独验证

当输入恰好连续、页号恰好顺序排列时，一些错误索引也可能得到看似正常的结果。测试需要主动破坏这些偶然关系。

| 要检查的设计 | 有辨别力的输入 | 应当观察什么 |
|---|---|---|
| 逻辑页到物理页的映射 | 交换物理页顺序，并使用跨页历史 | 结果仍按逻辑 token 顺序计算 |
| 不同请求的独立性 | 不同长度、不同页表的批次 | 每行使用自己的历史与 KV head |
| verify 的逐行因果范围 | 改变较晚候选位置的 K/V | 较早查询行的结果保持不受该位置影响 |
| Graph 填充行的写入保护 | 在真实 slot 旁加入 `slot=-1` | 真实缓存内容不被填充行覆盖 |
| 前缀恢复的顺序 | 打乱、重复选择 slot | 输出严格对应选择顺序，包括重复项 |
| 输入 token stride | 使用非连续 K/V 切片 | 与相同内容的连续输入写出一致缓存 |

这些检查对应的是布局和有效范围，不依赖某句自然语言恰好生成某个答案。它们也说明：一个输出张量形状正确、数值有限，还不足以证明模型读到了正确历史。

源码入口分别见[分页读取测试](../../tests/kernels/test_kv4_paged.py)、[因果与填充测试](../../tests/kernels/test_kv4_verify.py)、[stride、前缀恢复与长上下文测试](../../tests/kernels/test_kv4_materialize.py)。页的分配、引用计数、释放与投机提交则由 [Runtime 测试](../../tests/runtime)检查。

## 3. 为什么几条计算路径不要求逐 bit 一致

数学上相同的求和，换一种分组和顺序就可能有不同的浮点结果。当前设计还包含明确的精度转换：

- W4 GEMM 在程序内部使用 FP32 累积，FP16 主路径的最终输出及跨 split 原子合并目标为 FP16。
- 单行 W4 GEMV 有独立的向量乘法、归约与原子累加过程。
- KV4 decode 使用 FP32 恢复值和流式累积；grouped verify 将 K/V、概率块转成 FP16 参加矩阵乘法，再保持 FP32 的 softmax 状态与输出累积。
- KV4 split-KV 先保存 FP32 的部分状态，再通过另一个内核合并。

因此，对照应同时看绝对误差和相对误差。绝对误差帮助观察较小输出附近的偏差，相对 L2 帮助观察整体偏差；靠近零的参考值会使单元素相对误差不稳定。

允许误差需要结合输入尺度、精度和参考算法制定。数值参考、实际缓存值与具体容差都应在测试中明确；性能快慢不参与这些正确性断言。

## 4. 性能测量怎样对应设计问题

不同测量回答不同问题：

| 设计问题 | 对应测量 |
|---|---|
| W4 的解包与归约是否抵消了权重读取收益 | [W4 单算子](../../benchmarks/kernels/w4a16/README.md)，按输入行数和矩阵形状比较 |
| KV4 的成本主要出现在写入、Attention 还是前缀恢复 | [真实 Attention 层及分项](../../benchmarks/kernels/kv4/README.md) |
| 分片、归约和多个小内核怎样组成执行过程 | [Nsight 单层与整模分析](../../benchmarks/runtime/profile/README.md) |
| 单算子收益能否传递到请求延迟 | [完整引擎](../../benchmarks/runtime/engine/README.md)与[Graph 对照](../../benchmarks/runtime/cuda_graph/README.md) |

编译、调优与预热需要放在稳态测量之前。GPU Graph 计时主要观察设备执行，减少 Python 提交间隙；同步主机调用时间包含调用和同步成本。对由多个小内核组成的路径，两种数字尤其需要分开阅读。

分项测量也不能直接相加重建整层时间。独立测量改变了缓存状态、启动序列和工作区复用；例如“前缀恢复加拼接”本身已经包含恢复，若再加一次恢复耗时就会重复计算。

分析某个慢形状时，可以从设计中列出可能增加的工作，再通过时间线和分项确认。仅凭理论上的压缩比，无法判断实际主导成本。

## 5. 显存节省需要观察到哪一层

packed 数据与 scale 的字节数，回答常驻权重或缓存占多少空间。完整执行还会使用输入缩放张量、split-KV 部分状态、恢复后的浮点前缀、拼接结果和 Graph 保留的工作区。

因此，[整模显存测量](../../benchmarks/runtime/memory/README.md)同时观察进程采样峰值、PyTorch 张量分配峰值和内存池预留峰值。预留空间包含已分配空间，进程统计又覆盖 CUDA 上下文及库等成本，这些数字不应相加。

KV 池缩小几倍，描述的是其中一部分。前缀物化或模型加载时的临时空间，可能决定另一处峰值；这正是要将存储设计与完整执行一起评估的原因。

## 6. 测试入口

在服务器仓库根目录，使用项目环境与空闲 GPU：

```bash
CUDA_VISIBLE_DEVICES=1 .conda/bin/python -m pytest tests/kernels -q
```

这些测试用小张量和临时小模型验证数值与边界。模型目录、默认输入和性能测量命令由各 benchmark 的中文说明维护。
